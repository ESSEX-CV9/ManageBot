# 标题与 TAG 规范模块（titleGuard）

管理论坛帖子的**分类信息**：标题里的分类词和帖子挂的 TAG 不能互相矛盾。
检测到问题后先通知作者、给自改时间，到期不改机器人自己动手。管理组全程可覆盖、可还原。

完整设计见 [docs/标题与TAG规范模块设计.md](../../../docs/标题与TAG规范模块设计.md)。

```
titleGuard/

├── components/
│   ├── noticePanel.ts               通知消息 + 三个按钮
│   └── authorFixPanel.ts            作者自助面板（仅本人可见）
├── events/threadEvents.ts           ThreadCreate / ThreadUpdate
└── services/
    ├── types.ts                     引擎层类型
    ├── normalizer.ts                ① 归一化 + 原文坐标映射
    ├── segmenter.ts                 ② 切标记段 / 主体段
    ├── matcher.ts                   ③ 词典匹配（最大覆盖）
    ├── ruleEngine.ts                ④ 判定：撞了没有 + 归谁裁决
    ├── llmJudge.ts                  ⑤ 模型裁决（三步走 + 强制 tool call）
    ├── titleEdit.ts                 ⑥ 机制层：删/换动作怎么落到标题上
    ├── rewriter.ts                  ⑦ 整改方案（程序段 + 模型段 + 校验）
    ├── planner.ts                   打回重写的循环
    ├── enforcer.ts                  检测 / 建案 / 动手 / 还原
    ├── backfillQueue.ts             扫描 + 老帖慢速队列
    ├── titleGuardScheduler.ts       后台调度
    ├── titleGuardDatabase.ts        数据层（data/title-guard.sqlite）
    └── engine.test.ts               引擎层回归测试
```

`services/` 里 types / normalizer / segmenter / matcher / ruleEngine / titleEdit / rewriter
是**纯逻辑**：不碰 Discord、不碰数据库，可以脱离机器人单独跑测试。

```bash
npm run test:guard
```

## 调试台（改词表 / 验证判定，不用连 Discord）

```bash
npm run guard:ui        # 然后打开 http://127.0.0.1:5180
```

三个页签：

| 页签 | 干什么 |
| --- | --- |
| **单条测试** | 粘贴标题（可多行）+ 填 TAG，看引擎怎么切分、命中了哪些词、判了哪些规则、打算怎么改 |
| **批量分析** | 拖入 `/论坛标题 导出` 的 xlsx，全量跑一遍，可按处置/规则/关键词筛选，点任一行看完整判定过程 |
| **LLM 判定** | 填 API Key / 接口地址 / 模型（只存内存，不落盘），连通性自检 |
| **词表设置** | 改分类词 / 黑名单 / 白名单 / 互斥集合 / 分类优先级 / TAG 禁令 / TAG 映射，保存即生效 |

配好 LLM 后，凡是判成「需LLM定性」的条目下面都会出现「发起真实 LLM 判定」按钮，
点了会真调接口，并**按判定结果重算方案和通知**，能直接看到判定前后处置的变化。

单条测试会把引擎内部过程全摊开：

- **切分**：每段标成 前缀标记 / 中部标记 / 后缀标记 / 主体，命中的词在段内高亮
- **token**：标记段切出来的 token，标红的含分类词（删词时删的是整个 token）
- **关键词识别**：包括**落选的候选**和落选原因（被哪个更长的词盖住了）
- **判定结果**：每条规则、涉及哪些词和 TAG、能否直接判还是要 LLM
- **整改方案**：新标题、摘哪些 TAG、补哪些 TAG、保留哪个分类、依据是什么

后台跑的是**机器人同一套引擎代码**，所以这里看到的就是线上行为。唯一差别是不调 LLM——
需要 LLM 定性的会明确标成「需LLM定性」。

词表存在 `tools/seed-dict.json`，界面和离线分析脚本 `analyzeTitles.ts` 读的是同一份。

## 规则模型

### 四种冲突

| 编号 | 冲突 |
| --- | --- |
| `B` | 污染词：词面里裹着别组的受保护关键字（如某个词含着「纯爱」两个字却指 NTR） |
| `W` | 关键字 × 关键字 |
| `G` | TAG × TAG |
| `X` | TAG × 关键字（**有方向**，反过来不一定成立） |

三个维度是**分开配的**，这是最容易配错的地方。现行规则里 NTR 和 NTL 就是
「TAG 层互斥、关键字层兼容」——一部作品可以两样都有，标题里两个词并排写没问题，
但 TAG 只能挂一个。所以关键字维度必须配成「纯爱/NTR」和「纯爱/NTL」两组，
不能合成一组三个。

### 归谁裁决

只看一件事：**这个冲突靠哪些命中才成立。**

| | 谁裁决 |
| --- | --- |
| 光凭明写标签区里的词就能成立（前缀、后缀、TAG 一视同仁） | **程序**，按保留顺序直接改 |
| 非得搭上标题主体里的词才成立（含跨段冲突） | **模型** |

第二条是硬规矩，没有例外：**程序在标题主体里一概不下结论。**
一句话里的「绿帽」到底是在给作品归类还是在描述主角的癖好，光看字面切不开。

### 词档：本体词 / 关联词

词档**不参与路由**，它决定送进模型之后尺子有多严。

| 档 | 是什么 | 在标题主体里 |
| --- | --- | --- |
| **本体词** | 词面就是大家打进搜索框的那几个字 | 从严。留着就一定被搜到，跟它在句子里当什么成分无关，「只是个形容词」不是理由 |
| **关联词** | 语义相关，但词面不碰任何受保护关键字 | 结合上下文。问「是在归类还是在描述人物情节」，拿不准往描述靠 |

本体词是明确列举的少数几个，其余一律关联词。哪些词算本体由管理组配
（`/标题规范 词典 添加 词档:`，或导出 xlsx 改「词档」列再导回来），代码里不写死。

### 模型的三步

1. **定性** —— 这篇作品到底属于哪一类。证据强弱定死：
   标签区里作者自己写的 > 正文和首楼 > 帖子挂的 TAG。
   （TAG 排最后，因为标题是作者一个字一个字敲的，TAG 是发帖时随手点的。）
2. **核 TAG** —— 同时拿到「现在挂的」和「程序整改后会挂的」两份，**有权推翻程序**。
3. **逐处处理** —— 每一处命中三选一：删除 / 替换 / 保留。

## 三个关键实现细节

这三条是可靠性的地基，改代码时别破坏：

1. **匹配绝不跨段边界**（`matcher.ts` 逐段独立匹配）
   否则 `XXXX百合】破坏了美好XXXXX` 会被拼出一个根本不存在的「百合破坏」。

2. **最大覆盖，不是最左最长**（`matcher.ts` 的 `pickMaxCoverage`）
   `纯爱牛头人日记` 用最左最长会先吃掉黑名单词 `纯爱牛`、剩 `头人日记`，
   必须选覆盖更长的 `纯爱` + `牛头人` 才能正确判成分类冲突。

3. **书名号和引号不是标记括号**（`segmenter.ts` 的 `MARKER_BRACKETS`）
   只认 `【】[]〖〗〔〕()`。若把 `《》` 也当标记括号，
   `《真正的橘子味世界不允许百合破坏的存在！》` 整段会变成标记段而被直接改错。

## 模型的安全阀

**模型不写标题。** 它只对程序圈出来的那几处命中表态（删/换/留），标题由程序拼出来，
它碰不到一个自由字符。连「替换成什么」都只能从词表里挑（`titleEdit.resolveReplacement`）。

这是跟老版本最大的区别。老版本让模型直接交一个新标题，于是它会顺手做没让它做的事——
比如把整句「这辈子好像只能搞纯爱了」删掉，只因为里面有「纯爱」两个字。
校验能发现标题变短了，却发现不了作品被改性了。

提示词里每一处命中都写明了「删掉会连带没：……」，让模型自己权衡删还是换。

交回来的答卷要过 `rewriter.validateModelPlan`，放行的口子只有两个：

1. **本篇自己那一类的本体词**——作品是纯爱，标题里写「纯爱」，那不是污染。
2. **正文里的关联词**，模型明确判了保留并说清它在描述什么。

其余一律打回重写，并且告诉它**具体还剩哪条没解决**（`planner.buildRetryFeedback`），
最多打回一次，再不对才转人工。

论坛打开「首楼给模型」后，建案语义判定和作者第一次 AI 复核都会附首楼前 600 字。
定性光看标题做不了，分词把一个更长的词拦腰切断、切出来正好撞上污染词这种误伤
更是非看首楼不可。若 provider 的内容审核拦截，会自动去掉首楼重试。

论坛还可以单独打开「所有问题先经模型」。开着后，连程序原本能直接处理的标签区冲突和
TAG 冲突也会先让模型定性并形成完整方案，再过程序的安全校验；模型不可用时转人工，
不会绕过模型直接整改。两个论坛开关都可以在 `/标题规范 面板` 的「论坛」页批量设置，
也可以用 `/标题规范 论坛 添加` 的 `所有问题给llm` / `正文给llm` 参数修改。

LLM 不可用时（没配、被关、网络失败、被审核拦），归模型裁决的冲突全部挂起转人工；
归程序的那些通常照常跑，但打开「所有问题先经模型」的论坛同样会挂起转人工。

**调用姿势会自动降级**：`强制 tool call → 模型自行决定 → JSON 输出`，成功哪个记住哪个。
思考/推理模式的模型通常拒绝强制 `tool_choice`（报 `Thinking mode does not support this tool_choice`），
靠这条降级链兜住。JSON 模式下从回复正文里用括号配对抠出 JSON，能穿过模型的推理文字和 ``` 代码块。
无论走哪种姿势，「新标题只能是原标题删字」这道校验都照跑。

## 配置

**代码里不内置任何词典和互斥集合**，全部由管理组线上维护：

```
/标题规范 面板                                    （批量改权限/论坛/时间与开关）
/标题规范 词典 添加 / 删除 / 列表 / 导出 / 导入   （导出的 xlsx 含「词档」列）
/标题规范 互斥组 添加 / 移除 / 禁令 / 列表
/标题规范 tag映射 自动生成 / 查看 / 修改
```

LLM 走 `.env` 的 `TITLEGUARD_LLM_*`，其余走 `/标题规范 配置`。

**权限按能力发**，见 `services/titleGuardPermissions.ts`：
社区管理组是一堆身份组（风纪委员、执行管理……），各管一摊，所以不判「是不是管理员」，
而判「有没有这项能力」——`词表` / `设置` / `复核` / `覆盖` / `接警`（一项能力可以发给多个身份组），
用 `/标题规范 权限 授予` 发给对应身份组。

三条兜底：服主和 Discord 管理员永远全通；某项能力一个身份组都没配时回退到管理员判定
（也就是保持配置之前的行为）；发权限这件事本身不下放，只认管理员。

## 上线顺序

1. `/标题规范 扫描 <论坛> 静默:true` —— 只出 Excel 报表，不发通知不改动。
   摸清存量规模、检查误判、把白名单词补齐。
2. 词典定稿，**顺手把本体词标出来**——`/标题规范 词典 导出`，改「词档」列，再导入。
   本体词就是社区里大家真的会拿去搜的那几个分类名，其余保持「关联」。
3. `/标题规范 配置 启用:true 自动整改:true` —— 全套规则一次性生效。

老帖走慢速队列（默认 20 分钟一个）。慢是故意的：老帖发通知会顶帖，
慢速摊平才不会把论坛首页刷成翻出来的老帖。用 `/标题规范 队列 状态` 看进度和预计耗时。
